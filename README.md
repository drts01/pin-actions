# pin-actions

Automatically pin mutable GitHub Actions versions (e.g., `@v4`, `@main`) to their immutable 40-character commit SHAs.

Works as both a **CLI tool** and an **importable library**, scanning `.github/workflows/**/*.{yml,yaml}` and composite `action.yaml`/`action.yml` files.

## Installation

```bash
uv add pin-actions
```

Or via pip:
```bash
pip install pin-actions
```

## CLI Usage

### Basic Usage

```bash
pin-actions --path .github/workflows --github-token $GITHUB_TOKEN
```

### Options

Run `pin-actions --help` for full, always-up-to-date usage (generated by `pydantic-settings`' CLI support):

```
--path PATH                          Root directory to scan (default: .github/workflows)
--github-token, --pin-actions-token TOKEN  GitHub API token (env: GITHUB_TOKEN or PIN_ACTIONS_TOKEN)
--dry-run / --no-dry-run             Print changes without writing files
--concurrency N                      Max concurrent API calls (default: 5)
--max-retries N                      Retry attempts on rate limits (default: 5)
--github-api URL                     GitHub API base URL (default: https://api.github.com)
--update {major|minor|patch}         Update strategy for pinned semver tags: 'major' (absolute latest,
                                      crossing majors), 'minor' (same major, free within it), or 'patch'
                                      (same major.minor). Default: re-resolve exact tag/branch in comment
```

Flags are kebab-case (`--dry-run`, `--max-retries`), derived automatically from `Settings` field names.

### Examples

```bash
# Dry-run to see what would change
pin-actions --dry-run --github-token ghp_xxxx

# Process custom directory with 10 concurrent requests
pin-actions --path ./.workflows --concurrency 10

# Use GITHUB_TOKEN environment variable
export GITHUB_TOKEN=ghp_xxxx
pin-actions

# Update already-pinned semver tags to the absolute latest version, crossing major boundaries
# (e.g. actions/checkout@<sha>  # v4.0.5  ->  actions/checkout@<new-sha>  # v9.1.2)
pin-actions --update-to-latest-major

# Update to the latest version within the same major (e.g. v4.0.5 -> v4.9.0, never v5.x)
pin-actions --update minor

# Update to the latest patch within same major.minor (e.g. v4.2.3 -> v4.2.9)
pin-actions --update patch
```

### Version Constraints

By default, already-pinned refs are re-resolved against the *exact* tag/branch recorded in
their comment (see "What It Does" below) — a tag only moves if it's re-pushed to a new commit.

`--update-to-latest-major` / `--update-to-latest-minor` change this: instead of re-resolving the
same tag, `pin-actions` looks up all tags on the remote repo (via `GET /repos/{owner}/{repo}/tags`)
and picks the highest [`packaging.version`](https://packaging.pypa.io/en/stable/version.html)-parseable
tag matching the constraint relative to the currently pinned tag:

| Mode | Constraint | Example |
|---|---|---|
| `--update major` | absolute latest tag on the repo, can cross major versions | `v4.0.5` → `v9.1.2` |
| `--update minor` | same major version, free within it | `v4.0.5` → `v4.9.0` (never `v5.x`) |
| `--update patch` | same major.minor, free within patch | `v4.2.3` → `v4.2.9` (never `v4.3.x`) |

**Constraint degradation by precision**: When the current comment has fewer components than the
constraint requires, the constraint degrades to what the comment specifies. For example, a
major-only comment (`v4`) with `--update patch` degrades to major-only matching (`v4.x`), picking
the latest v4 tag regardless of minor/patch — this prevents spuriously narrowing to v4.0.x.
Similarly, `v4.0` with `--update patch` matches any v4.0.x.

| Original comment | Flag | Effective constraint | Example |
|---|---|---|---|
| `v4` | `--update patch` | same major only | `v4.0.1` or `v4.9.0` → pick `v4.9.0` |
| `v4.0` | `--update patch` | same major.minor | `v4.0.1` or `v4.1.0` → pick `v4.0.1` |
| `v4` | `--update minor` | same major only | `v4.0.1` or `v5.0.0` → pick `v4.9.5` |

Non-semver comments (branch names like `main`) are left frozen unless `--update-branches` is also
passed. If no tag on the remote satisfies the constraint, `pin-actions` prints a warning to stderr
and leaves that entry untouched:

```
pin-actions: warning: no tag matching version constraint for actions/checkout@v4.0.5; leaving pinned as-is
```

**Precision preservation**: the rewritten tag comment matches the precision (number of
dot-separated components) of the comment it's replacing — a rewrite never "upgrades" how
specific your pin looks. For example:

| Original comment | Flag | Winning remote tag | New comment |
|---|---|---|---|
| `v4` | `--update-to-latest-minor` | `v4.9.0` | `v4` |
| `v4.0.5` | `--update-to-latest-major` | `v9.1.2` | `v9.1.2` |
| `v4.0` | `--update-to-latest-minor` | `v4.9.3` | `v4.9` |

## Error Handling

Library functions **raise, they don't swallow** — the caller decides how to handle failures. The CLI is the only layer that catches exceptions and converts them to stderr messages + exit codes.

```python
from pin_actions import PinActionsError, InvalidRefError, YAMLParseError

try:
    modified = await pin_file(client, path)
except YAMLParseError as exc:
    print(f"Bad YAML in {exc.path}: {exc.reason}")
except InvalidRefError as exc:
    print(f"{exc.repo}@{exc.ref} does not exist")
except PinActionsError as exc:
    print(f"Pin failed: {exc}")
```

Exception hierarchy (all importable from `pin_actions` or `pin_actions.errors`):

```
PinActionsError                  # base
├── YAMLParseError               # malformed YAML
└── GitHubAPIError               # base for all API failures
    ├── InvalidRefError          # 404: ref doesn't exist
    ├── RateLimitExhaustedError  # retries exhausted on 429/403
    └── NetworkError             # unrecoverable network failure
```

`run()` processes files concurrently and, if any fail, raises a Python 3.11+ `ExceptionGroup[PinActionsError]` containing one exception per failed file (successful files are not returned in that case — call `pin_file()` per-file if you need partial results alongside errors).

## Library Usage

### Import and Pin Files

```python
import asyncio
from pathlib import Path
from pin_actions import GitHubClient, run
from pin_actions.config import Settings

async def main():
    settings = Settings(
        path=Path(".github/workflows"),
        github_token="ghp_xxxx",
        dry_run=False,
        concurrency=5,
    )
    modified = await run(settings)
    print(f"Modified {len(modified)} file(s)")

asyncio.run(main())
```

### Use Client Directly

```python
import asyncio
from pin_actions import GitHubClient

async def main():
    client = GitHubClient(token="ghp_xxxx", concurrency=10)

    # Resolve mutable ref to commit SHA
    sha = await client.resolve_sha("actions/checkout", "v4")
    print(f"actions/checkout@v4 -> {sha}")

asyncio.run(main())
```

## What It Does

Before:
```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@main
      - uses: ./local-action@v1
```

After:
```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b  # v4
      - uses: actions/setup-python@f1e2d3c4b5a6f7e8d9c0b1a2f3e4d5c6b7a8f9e  # main
      - uses: ./local-action@v1
```

### Checkout Another Repo (`with.ref`)

`actions/checkout` steps that check out a different repo (via `with.repository`) can also have their `with.ref` pinned:

Before:
```yaml
jobs:
  build:
    steps:
      - name: Checkout this repo
        uses: actions/checkout@v4
      - name: Checkout another repo at a tag
        uses: actions/checkout@v4
        with:
          repository: owner/other-repo
          ref: v3.0.0
```

After:
```yaml
jobs:
  build:
    steps:
      - name: Checkout this repo
        uses: actions/checkout@a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b  # v4
      - name: Checkout another repo at a tag
        uses: actions/checkout@a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b  # v4
        with:
          repository: owner/other-repo
          ref: d9e8f7g6h5i4j3k2l1m0n9o8p7q6r5s4t3u2v1w0  # v3.0.0
```

**Scope**: Only `actions/checkout` steps with **both** `with.repository` and `with.ref` fields present are pinned. Steps without a `with.repository` sibling are skipped (current-repo context is not available to the tool).

Features:
- ✅ Resolves mutable refs (branches, tags, short SHAs) to full commit SHAs
- ✅ Updates already-pinned refs: re-resolves the tag/branch recorded in the trailing comment on every run and rewrites the SHA if it has moved (mirrors [`mheap/pin-github-action`](https://github.com/mheap/pin-github-action)'s default behavior) — a bare SHA with no comment is left untouched since there's no tag to re-resolve against
- ✅ Pins `actions/checkout` `with.ref` parameters (checkout-another-repo workflows) alongside `uses:` values
- ✅ Skips local actions (`./...`) and Docker actions (`docker://...`)
- ✅ Thread-safe async/concurrent request handling with rate-limit backoff
- ✅ No-op when nothing has changed (re-running with unmoved tags produces identical output)
- ✅ Preserves comments and formatting (round-trip YAML via `yamlrocks`)
- ✅ Optional `--update-to-latest-major`/`--update-to-latest-minor` to move already-pinned tags forward to the absolute latest / latest-within-same-major version, preserving the original comment's precision (`v4` stays `v4`), with `--update-branches` to also re-resolve branch refs in that mode (see [Version Constraints](#version-constraints))

## Performance

- **Concurrent requests**: Limited by `--concurrency` flag (default 5) to avoid API rate limits
- **Caching**: In-process cache prevents duplicate API calls for same ref within a run
- **Rate-limit handling**: Exponential backoff on 429/403 with `Retry-After` header support
- **Dry-run**: Parse and resolve refs without writing files
- **Caching (future)**: Response-level caching via [Hishel](https://github.com/karpetrosyan/hishel) will be added once Hishel supports `httpx2`; the manual lock-guarded cache handles ref-resolution dedup in the meantime

## Design

| Component | Purpose |
|-----------|---------|
| `GitHubClient` | Async HTTP client with rate-limit backoff, caching, and semaphore-bounded concurrency; `list_tags()` lists all tags (paginated, cached per-repo) for version-constrained selection |
| `versioning.py` | Semver-aware tag selection (`packaging.version`): `select_latest_tag()` picks the highest version satisfying `--update-to-latest-major` (no constraint)/`--update-to-latest-minor` (same-major constraint) relative to the currently pinned tag, and re-renders the winning tag to match the original comment's precision/prefix |
| `Settings` | `pydantic-settings`-based CLI/env config; CLI parsing (`--help`, kebab-case flags) enabled via `_cli_parse_args=True` at `Settings()` call time in `main()` only — not baked into `model_config`, so direct instantiation (library/tests) never touches `sys.argv` |
| `errors.py` | Exception hierarchy (`PinActionsError` base); library raises, CLI (`main()`) is the sole catch point |
| `pin_file()` | Parse (via `yamlrocks`) and rewrite individual workflow files |
| `run()` | Main orchestrator: glob files, resolve refs, write results |
| `yamlrocks` | Round-trip YAML parser (Rust-backed). `doc.walk()` finds `uses:` key paths; indexed assignment (`doc[k1][k2]... = value`) writes through to the AST, preserving comments/formatting on untouched lines |

Thread-safety:
- `asyncio.Semaphore` bounds concurrent API requests
- `threading.Lock` guards response cache dict (safe for multi-loop usage)

## Testing

Run test suite:
```bash
pytest tests/
```

With coverage:
```bash
pytest --cov=pin_actions tests/
```

Tests cover:
- `uses:` string parsing (mutable refs, sub-paths, comments)
- Caching and deduplication
- Rate-limit retry logic (429, 403), including exhaustion raising `RateLimitExhaustedError`
- Invalid ref (404) raising `InvalidRefError`
- Malformed YAML raising `YAMLParseError`
- Partial-batch failures in `run()` raising `ExceptionGroup[PinActionsError]`
- File modification, dry-run mode, and comment/formatting preservation
- Batch workflow processing
- Semver tag parsing/selection (`versioning.py`) and `GitHubClient.list_tags()` pagination/caching
- Version-constrained updates (`--update-to-latest-major`/`--update-to-latest-minor`/`--update-branches`), including the no-match warning path
